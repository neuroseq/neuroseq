================================================================================

GitHub issue #506 ("Enhancement of suite2p analysis pipeline") lists three
asks. Investigation (read every file below in full before starting) found:

  1. "Enable quick analysis of the recordings without cellpose: Right now
     cellpose masks are obligatory for suite2p analysis." — NOT implemented.
     `run_suite2p_pipeline()` hard-requires a 2D Cellpose label mask.
  2. "During the suite2p analysis provide a window with more detailed logs."
     — NOT implemented. Suite2p logs richly via stdlib `logging`, all of it
     silently discarded; the GUI shows one overwritten line of progress text.
  3. "Cellpose import: exclusion/inclusion criteria add an option to set in %
     from the image size." — ALREADY implemented AND already has passing
     tests (`AreasOfInterestConfig.coordinate_mode`, the "% of FOV" combo,
     `_current_square_aoi`/`_current_circle_aoi`/`_set_aoi_controls` percent
     conversion, and `test_dialog_aoi_percentage_mode_uses_centres_and_fov_size`
     / `test_dialog_aoi_pixel_mode_uses_square_centre` in
     tests/test_cellpose_aoi_mapping.py). Do NOT re-implement or re-litigate
     this — the only real gap is that the percent-mode round trip through
     `_set_aoi_controls` (config -> spinboxes) is untested; only pixel mode
     is (test at line 305-322). Add ONE small test to close that gap. This
     item is otherwise DONE — don't spend time here beyond that one test.

BACKGROUND — read before touching anything
────────────────────────────────────────────────────────────────────────────

- `run_suite2p_pipeline(tif_paths, masks, params, *, work_dir=None,
  progress=None)` (importer_tif.py:245-465) is the only place a Cellpose
  mask is consumed. Validation: `if masks.ndim != 2: raise ValueError(...)`
  (importer_tif.py:261-262), and a shape check against the decoded TIFF
  frame size (importer_tif.py:368-371). The mask is turned into a Suite2p
  `stat` array by `_masks_to_stat(masks, Ly, Lx)` (importer_tif.py:218-242,
  called at :383), which uses `suite2p.detection.roi_stats` /
  `assign_overlaps` on a hand-built `stat` list (one dict per Cellpose
  label, `ypix`/`xpix`/`npix`/`lam`/`med`).

- The pipeline never calls Suite2p's own registration step — it goes
  straight from `s2io.tiff_to_binary(...)` (importer_tif.py:357) to
  `mean_image = f_bin.data.mean(axis=0)` (importer_tif.py:380). So
  `yrange`/`xrange` for detection must be the full frame, `[0, Ly]` /
  `[0, Lx]` — there is no registration crop to reuse.

- Suite2p 1.1.0 (the version pinned in this repo's venv) ships
  `suite2p.detection.detection_wrapper`, confirmed via
  `inspect.signature`:

      detection_wrapper(f_reg, diameter=[12.0, 12.0], tau=1.0, fs=30,
          meanImg_chan2=None, yrange=None, xrange=None, badframes=None,
          mov=None, preclassify=0.0, classifier_path=None,
          settings=default_settings()["detection"], device=torch.device(...))
      -> (new_settings: dict, stat: np.ndarray, redcell: np.ndarray | None)

  `f_reg` just needs a `.shape` returning `(n_frames, Ly, Lx)` — confirmed
  `suite2p.io.BinaryFile.shape` is a property returning exactly that, so
  the already-open `f_bin` (importer_tif.py:373) can be passed directly,
  no new binary read needed. `redcell` is only populated when
  `meanImg_chan2` is given (2nd-channel red-cell detection) — do not wire
  that up, it's out of scope; pass `meanImg_chan2=None` implicitly (leave
  the kwarg unset) and ignore the returned `redcell`.

  `defaults["detection"]` (where `defaults = suite2p.default_settings()`,
  already computed at importer_tif.py:318) is the settings dict to pass —
  its `"algorithm"` key defaults to `"sparsery"`, which is what to use; no
  algorithm-choice UI (confirmed decision — do not add one).

- Every Suite2p submodule logs via `logging.getLogger(__name__)` under the
  `suite2p` namespace and none of them set `propagate=False` (confirmed by
  grepping every `.venv/lib/python3.12/site-packages/suite2p/**/*.py`), so
  a `logging.Handler` attached to `logging.getLogger("suite2p")` for the
  duration of a pipeline run will receive everything Suite2p logs
  internally (binning messages, timing, "Removing N ROIs with snr < ...",
  etc.) even though `run_suite2p_pipeline` calls Suite2p's low-level
  functions directly rather than `suite2p.pipeline`. `importer_tif.py`'s
  own `logger = logging.getLogger(__name__)` (importer_tif.py:24, i.e.
  `"neuroseq.importer_tif"`) is worth capturing the same way — its
  `logger.info`/`logger.warning` calls at importer_tif.py:337,343,365
  currently go nowhere the user can see.

- `_PipelineWorker.run()` (tif_import_dialog.py:78-101) executes on a
  background `QThread`; its `progress`/`finished`/`failed` signals
  (tif_import_dialog.py:61-63) are already used to marshal data back to
  the GUI thread safely via Qt's queued-connection mechanism. Follow the
  exact same pattern for the new log signal — do not touch Qt widgets
  from inside `run()` directly.

- Existing reusable log-widget pattern: `stdp_window_dialog.py:279-282`
  builds a read-only `QtWidgets.QPlainTextEdit` capped at

       class _QtLogHandler(logging.Handler):
           """Formats log records and hands them to a thread-safe sink.

           The sink is expected to be a Qt signal's `.emit` (queued across
           threads automatically by Qt), so `emit()` here is safe to call
           from a background QThread.
           """

           def __init__(self, sink: Callable[[str], None]) -> None:
               super().__init__(level=logging.INFO)
               self._sink = sink
               self.setFormatter(logging.Formatter("%(levelname)s: %(message)s"))

           def emit(self, record: logging.LogRecord) -> None:
               self._sink(self.format(record))
