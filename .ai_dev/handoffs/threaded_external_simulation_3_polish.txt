3. Test #9, in `tests/test_threaded_external_dispatch.py`:

```python
def test_progress_dialog_cancel_button_text_lifecycle(qtbot, gui):
    """The dialog shows a Cancel button only while a sim runs."""
    import threading
    from neuroseq.data import Experiment

    block = threading.Event()

    def _blocking_simulate(stims_dict, simulation_time, params, progress):
        progress(0.0)
        block.wait(timeout=5.0)
        return Experiment(name="text_lifecycle", duration=0.0,
                          timepoints=[], data=[])

    _wire_fake_external_simulator(gui, _blocking_simulate)

    # Before dispatch: no cancel button (the default state set in
    # _create_progressbar).
    assert gui.progress_dialog.findChild(QtWidgets.QPushButton) is None or (
        # On some platforms findChild returns the hidden button; check it.
        not gui.progress_dialog.findChild(QtWidgets.QPushButton).isVisible()
    )

    # Dispatch.
    gui._do_external_simulation(1.0)
    worker = gui._external_sim_worker
    qtbot.waitUntil(lambda: gui.progress_dialog.isVisible(), timeout=2000)

    # During dispatch the cancel button is present and clickable.
    cancel_btn = gui.progress_dialog.findChild(QtWidgets.QPushButton)
    assert cancel_btn is not None
    assert cancel_btn.isEnabled()

    # Release the worker.
    block.set()
    with qtbot.waitSignal(worker.finished, timeout=5000):
        pass

    # After completion the dialog is back to no-cancel.
    assert gui.progress_dialog.findChild(QtWidgets.QPushButton) is None or (
        not gui.progress_dialog.findChild(QtWidgets.QPushButton).isVisible()
    )
```

   Note: QProgressDialog's "button shows/hides" semantics differ
   slightly between Qt 5 and 6. The two-clause assertion above is
   defensive; if the test fails locally check what
   `findChild(QPushButton)` returns in your Qt version and tighten
   the assertion.

MANUAL ROLLOUT CHECKLIST
────────────────────────────────────────────────────────────────────────────────────────────

Run these on real hardware after all automated tests pass. None of
them should be skipped — the threaded path's failure modes are
exactly the ones the test harness can't catch (real Qt event loop
under user input, real numpy/numba work releasing the GIL).

  □ Launch a 10 000-phrase ELiSe training run.
  □ Mid-run, drag the trace widget's ROI. The selection must
    respond fluidly (no lag, no frame drops).
  □ Mid-run, switch between traces in the `cmb_data` dropdown
    (e.g. somatic_potential_u → firing_rate_r). The trace must
    redraw.
  □ Mid-run, open the Heatmap. It must render synapse weights from
    the *pre-dispatch* checkpoint (the new weights aren't available
    yet).
  □ Mid-run, click "Save project". The save dialog must open and
    save the *current* project (without the still-running sim's
    result, by design).
  □ Mid-run, click "Cancel" on the progress dialog. The dialog
    must close within ~1 s and the "Simulation cancelled" info
    box must appear.
  □ Mid-run, close the main window. The thread must drain within
    2 s; no orphan thread warnings in stderr.
  □ Mid-run, swap to a different example project via the menu.
    After the original sim completes, the project-swap warning
    dialog must appear and the experiment must be in the
    original (now non-active) project.
  □ Run a deliberately-erroring fake simulator. The error box
    must appear and the project must be unchanged.
  □ Verify CPU usage during the run shows the worker thread
    actively churning (e.g. `htop` or Activity Monitor).

────────────────────────────────────────────────────────────────────────────────────────────
KNOWN LIMITATIONS (acceptable, document in the spec)
────────────────────────────────────────────────────────────────────────────────────────────

  • Only one external sim at a time. Re-entrant dispatch is a no-op
    by design. Users who want to compare multiple parameter
    settings should script their runs sequentially.

  • The simulator is still pure Python+numpy. CPU utilisation by
    the worker is bounded by the GIL release frequency in
    `elise.Network.__call__`. A future numba-jit pass on the inner
    loop would multiply throughput by 10–100× without changing the
    threading design.

  • If a main-thread code path is later added that reads
    `project.external_simulator.simulated_time_seconds` (or any
    other mutating attribute on the simulator) while a sim is
    running, locking will be required. As of this work no such
    path exists.
