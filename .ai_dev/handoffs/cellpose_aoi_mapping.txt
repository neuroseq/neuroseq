cellpose_aoi_mapping — "Custom with areas of interest" mapping strategy in the Cellpose import dialog [IMPLEMENTED]
==================================================================================================================

Add a third Mapping Strategy to the Cellpose import dialog: "Custom with areas of
interest". When active, the user defines two shapes on the FOV — a square (the
region where the laser power distribution is well-behaved) and a circle (the
region where power cannot be generated properly). Each shape can be marked
preferential or exclusion. Cells whose centroid falls inside a preferential
shape get the lowest stim IDs (starting at 0). Cells inside an exclusion shape
get the highest stim IDs. Exclusion takes priority where shapes overlap.

The result is fed into the existing custom-mapping line edit (autofilled),
which is what already drives `_parse_custom_mapping` and `_update_preview_mapping`.

Files to change:
    src/neuroseq/importer_cellpose.py           (add AOI dataclasses, mapping helper, persist)
    src/neuroseq/cellpose_import_dialog.py      (radio button, sub-group UI, wire-up)
    src/neuroseq/cell_overlay_widget.py         (draw + drag/resize shapes, emit changes)
    src/neuroseq/io.py                          (serialise/deserialise AOI config)

Files to create:
    tests/test_cellpose_aoi_mapping.py          (logic + UI tests)


────────────────────────────────────────────────────────────────────────────────────────────
COORDINATE SYSTEMS — read before touching the overlay
────────────────────────────────────────────────────────────────────────────────────────────

The cellpose importer calls `np.flipud()` on both the image and the segmentation
(`importer_cellpose.py:162` and `:278`) so that pygfx's default y-up camera
displays the original image right-way-up (Fiji-style). Consequences:

- In pygfx WORLD coords (what `OverlayView` operates in): origin is at the
  bottom-left of the displayed image. world_x ∈ [0, W], world_y ∈ [0, H].
  `_label_centers` and `pointer_move` already use world coords directly
  (see `cell_overlay_widget.py:269-273` and `:486-506`).

- In USER-facing coords (what goes into the text fields and is exposed to the
  reviewer): origin is at the top-left of the displayed image, y grows
  downward. For a point: `world_x = user_x`, `world_y = H - user_y`.
  For a square defined by its top-left corner (user_x, user_y) and side s:
  the world-coords AABB is `x ∈ [user_x, user_x + s]`,
  `y ∈ [H - user_y - s, H - user_y]`.

Centralise this conversion in `aoi_shapes.py` (see below) so the dialog, the
overlay, and the mapping helper all agree.

3.  ADD `generate_aoi_stimulus_mapping`:

        def generate_aoi_stimulus_mapping(
            original_ids: np.ndarray | None,
            label_centers: dict[int, tuple[float, float]],
            config: AreasOfInterestConfig,
            image_height: int,
        ) -> dict[int, int]:
            """Map cellpose IDs to stim IDs using AOI roles.

            `label_centers` is the {cellpose_id: (world_x, world_y)} map produced
            by OverlayView._compute_label_centers (i.e. world coords). The
            shapes in `config` are in user coords; convert before testing.
            """

    Logic, in order:
        a. If `original_ids` is None → return {}.
        b. Build a list of (cellpose_id, world_x, world_y) for every id in
           `original_ids` that has a centroid in `label_centers`. Cells
           without a centroid (degenerate masks) are dropped silently.
        c. For each cell, evaluate membership:
              in_square = config.square.enabled and point_in_square(world_x, H - world_y, square)
              in_circle = config.circle.enabled and point_in_circle(world_x, H - world_y, circle)
           Note: convert world_y → user_y via `H - world_y` so the shape's user
           coords are directly comparable.
        d. Compute the role for each cell:
              - exclusion if (square is exclusion AND in_square) OR
                              (circle is exclusion AND in_circle)
              - preferential if NOT exclusion AND
                              ((square is preferential AND in_square) OR
                               (circle is preferential AND in_circle))
              - neutral otherwise
           Exclusion always wins over preferential — required by spec.
        e. Sort each tier by cellpose_id ascending.
        f. Concatenate: [preferential…, neutral…, exclusion…].
        g. Assign stim_id = position in that concatenated list (0..T-1).
        h. Return `{stim_id: cellpose_id}` — same shape as
           `generate_linear_stimulus_mapping` and the same shape consumed by
           the rest of the dialog.

    Helpers — implement as plain free functions in the same module:

        def point_in_square(ux: float, uy: float, sq: SquareAOI) -> bool:
            return sq.x <= ux <= sq.x + sq.side and sq.y <= uy <= sq.y + sq.side

        def point_in_circle(ux: float, uy: float, c: CircleAOI) -> bool:
            r = c.diameter / 2.0
            return (ux - c.cx) ** 2 + (uy - c.cy) ** 2 <= r * r

────────────────────────────────────────────────────────────────────────────────────────────
NOTES
────────────────────────────────────────────────────────────────────────────────────────────

- The dialog's _generate_stimulus_mapping("Custom with areas of interest")
  must return the same mapping that's been autofilled into the line edit;
  the cleanest way is to call the AOI helper directly rather than parsing
  the line edit a second time, so we never rely on round-tripping our own
  serialisation.

- The custom mapping line edit stays editable in AOI mode (the user can hand-
  tweak after auto-fill). But any subsequent change to a shape input will
  OVERWRITE manual edits — confirmed in planning. No need to detect "user
  has hand-edited" state.

- The existing `_apply_existing_mapping` code path (line 496) sorts and
  filters identity pairs out of the custom mapping. Keep the AOI autofill
  doing the same — call into a shared helper so the two paths produce
  identical strings for the same mapping.

- pygfx LineGraphic + screen-space ScatterGraphic handles are already used
  elsewhere in this codebase via fastplotlib (see `stim_widget.py` and
  `gridlines.py` if you need precedent). Don't introduce QPainter overlays
  — the user explicitly chose the pygfx route.

- Pan/zoom lock during drag: `FullScreenFPLWidget` extends the fastplotlib
  figure widget, whose subplot controller exposes `enabled` (bool). If
  that's not present on this version, stop event propagation on the down
  handler and the controller won't get the event.

- Persist the show_shapes flag too: the user may turn off shapes visually
  for screenshots, and that should survive save/load.


────────────────────────────────────────────────────────────────────────────────────────────
NON-GOALS
────────────────────────────────────────────────────────────────────────────────────────────

- ROTATING shapes. Square is axis-aligned. Circle is a circle, not an
  ellipse.
- MORE THAN ONE square or circle. Exactly one of each.
- SHAPE TYPES BEYOND SQUARE/CIRCLE. No polygon, no rectangle, no annulus.
- AUTO-DETECTING the AOIs from the image. The user places them by hand or
  via the text fields.
- APPLYING THE AOIs OUTSIDE THE CELLPOSE IMPORT DIALOG. The downstream
  consumers (hardware export, etc.) only see the resulting stim-to-cellpose
  mapping. The AOI config travels with the import result for round-tripping
  but isn't consulted elsewhere.
- CHANGING the existing "Custom" mapping behaviour. It's untouched —
  hand-typed mappings still work as before.
