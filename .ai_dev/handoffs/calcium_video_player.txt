calcium_video_player — Raw calcium-TIFF video player panel with stim-triggered red-cross cell labeling and labeled-video export
================================================================================================================================

Add a new panel, `CalciumVideoWidget`, placed in the same right-hand splitter
as the existing "Heatmap" (Synapses) and "Spatial Footprints" panels, toggled
from the View menu/toolbar the same way. It plays back the RAW multi-frame
calcium-imaging TIFF (the same movie a Suite2p/Cellpose TIFF import already
processes into traces/segmentation) frame-by-frame, synced to the app's
shared playback timeline (the same time cursor that scrubs
trace/stim/spike/heatmap panels together). A dropdown picks which StimArray
(or "All arrays combined") determines "this cell was stimulated in this
frame"; stimulated cells get a red cross drawn at their Cellpose-segmentation
centroid, for every frame whose time window overlaps a nonzero stim sample
for that cell. A "Save labeled video…" button exports a new multi-frame TIFF
with the crosses burned into the pixel data.

If the project already has a raw video associated (see below — it does NOT
today; that's part of this handoff), the panel plays it immediately. If not,
it shows an "Import Video" button (mirroring `SpatialFootprintWidget`'s own
`import_requested` signal pattern) that lets the user pick TIFF file(s)
purely for playback, with no Suite2p/Cellpose processing involved.

IMPORTANT — verified by reading the code, not assumed: **the raw movie's
pixel data is never retained anywhere today.** `run_suite2p_pipeline`/
`run_roi_average_pipeline` (`importer_tif.py`) take `tif_paths: list[Path]`
as a plain function parameter and return only derived arrays (traces,
spikes, a single `mean_image` projection) — the paths are never stored on
`Project` or any result object, and the pipeline's temp Suite2p cache is
explicitly deleted in a `finally` block (`importer_tif.py:553-559`,
`shutil.rmtree(tmp_root, ...)`). `CellposeImportResult.image_path` is NOT
the raw movie — it's the single 2D projection image the user segmented
(`cellpose_import_dialog.py`'s `_browse_image_file`, filter
`"Image files (*.png *.tif *.tiff)"`, one image). So "reuse the project's
TIFF if available" requires adding a new small piece of persisted state to
`Project` (a path list + fps), populated at the end of a successful TIFF
import. That's the first thing to build below — everything else depends on
it existing.

   same convention `OverlayView` uses for its own pixel lookups — see the

   do NOT reuse `_compute_cell_centroids` as-is. Add a new, simpler function

        from scipy import ndimage

        def compute_cell_centroids(
            segmentation: np.ndarray,
        ) -> dict[int, tuple[float, float]]:
            """Each cell id's centroid in the SAME (world x, world y) = (col, row)
            convention OverlayView's own pixel lookups use (no y-flip) - i.e. the
            centroid is directly usable as a graphic's world position on top of
            the same image/segmentation this app already renders."""
            unique_ids = [int(i) for i in np.unique(segmentation) if i >= 0]
            centroids: dict[int, tuple[float, float]] = {}
            for cell_id in unique_ids:
                row, col = ndimage.center_of_mass(segmentation == cell_id)
                centroids[cell_id] = (float(col), float(row))
            return centroids

   `scipy.ndimage` is already imported elsewhere in this codebase
   (`spatial_footprint_widget.py:8` uses `binary_erosion`,
   `exporter_syscon2.py:13` uses `distance_transform_edt`) — no new
   dependency. `scikit-image`/`regionprops` is NOT a dependency anywhere;
   don't reach for it.

11. No video-writing library exists in this codebase today.
    `grep -rn "tifffile.imwrite\|TiffWriter\|imwrite(" src/neuroseq/` and
    `grep -rln "cv2\|VideoWriter\|imageio\|matplotlib.animation" src/neuroseq/`
    both return nothing — only `tifffile.imread` is used
    (`importer_tif.py:114`). `pyproject.toml` declares `pillow`, `scipy`,
    `tifffile` — no `opencv-python`/`imageio`/`scikit-image`. DECISION for
    this handoff: "Save labeled video…" exports a multi-frame TIFF via
    `tifffile.imwrite`/`tifffile.TiffWriter` (already a dependency), NOT an
    `.mp4`/`.avi` — adding a video-codec dependency for this is out of scope
    (see NON-GOALS). Converting to RGB is required regardless: raw calcium
    TIFFs are single-channel; a genuinely red cross needs 3 channels. Build
    each output frame as `uint8` RGB (normalize the raw frame to 0-255,
    replicate across R/G/B for the background, then set the cross pixels to
    pure `(255, 0, 0)`), and write with
    `tifffile.imwrite(path, iter_of_rgb_frames, photometric="rgb")` — use
    `TiffWriter` in "append" mode (`tifffile.TiffWriter(path)` then
    `.write(frame, photometric="rgb")` per frame in a loop) so the whole
    output stack is never held in memory at once, matching the raw input's
    own frame-at-a-time reading (see point 12).

12. Lazy frame access. Given a raw movie can be tens of thousands of frames
    at 512×512 (see this project's CLAUDE.md: 27000 frames, 15 min at
    30 Hz), do NOT load the whole stack into memory. `tifffile` supports
    per-page reads: `tifffile.TiffFile(path)` then `.pages[frame_index].asarray()`
    for one frame, or `tifffile.memmap(path)` for a memory-mapped array
    (no verified precedent for either specific call in this codebase today —
    VERIFY the exact API against the installed `tifffile` version's docs
    before committing to one; both are standard `tifffile` features). When
    `calcium_video_paths` has more than one file (the Suite2p pipeline
    already supports multi-file TIFF stacks as one combined movie via
    `tif_paths: list[Path]`), treat them as one continuous sequence
    concatenated in the given list order — VERIFY this is exactly how
    `run_suite2p_pipeline`/`run_roi_average_pipeline` interpret multiple
    paths today (read `importer_tif.py` before assuming simple
    concatenation is correct) so frame-index-to-file-and-page math in the
    new widget matches what Suite2p itself already did with the same files.

    class CalciumVideoWidget(QtWidgets.QWidget):
        """Plays back the project's raw calcium-imaging TIFF, synced to the
        shared playback timeline, with red crosses on cells a chosen
        StimArray (or all of them combined) marks as stimulated in the
        current frame."""

        def set_video_paths(self, paths: list[Path], fps: float | None) -> None:

            ...

Notes on the sketch:
  - `_stimulated_cellpose_ids_at` needs `stim_id_to_cellpose_id` (from
    `cell_overlay_widget.py`), not `cellpose_to_stim_id` — a StimArray
    column index IS a stim_id; converting it to a cell to look up its
    centroid needs stim_id -> cellpose_id.
  - The widget's OWN "Import Video" flow (triggered via `import_requested`,
    handled in `gui.py`) is a LIGHTWEIGHT file pick + fps prompt, calling
    `self.project.set_calcium_video(paths, fps)` then
    `self.calcium_video_widget.set_video_paths(paths, fps)` — it must NOT
    go through `TifImportDialog`/`run_suite2p_pipeline` (see BACKGROUND
    point 8's note on `_on_calcium_video_import_requested`).
  - The empty/import-state UI (shown when `self._paths` is empty or the
    first path doesn't resolve on disk) should look like
    `SpatialFootprintWidget`'s own empty state — check
    `set_empty_message`/whatever `CellOverlayWidget` exposes for "no data
    yet" and reuse the same visual language if this widget also embeds a
    `CellOverlayWidget`-style frame (it doesn't have to — a plain
    fastplotlib image is enough — but keep the EMPTY STATE MESSAGE STYLING
    consistent, e.g. same font/QLabel treatment).

NOTES
────────────────────────────────────────────────────────────────────────────────────────────

- Frame-time-to-stim-row alignment: for a video frame `i` (0-indexed) at
  frame rate `fps`, its time window is `[i/fps, (i+1)/fps)` seconds. For a
  given StimArray with its own `dt`, the overlapping row range is
  `[floor(i/fps/dt), ceil((i+1)/fps/dt))` — a cell counts as stimulated in
  that frame if `np.any(stim_array.values[row_start:row_stop, column] != 0)`
  for that cell's stim_id column. Do this per selected array independently
  (BACKGROUND point 10) and union the resulting stimulated stim_ids across
  arrays for "All arrays combined".
- Colour consistency: crosses don't need to match `neuron_indices_to_colors`
  (they're a fixed red, per the user's explicit request), so no colour-
  matching work is needed here, unlike the Spatial Footprints panel.
- Keep the widget resilient to `Project.calcium_video_paths` pointing at a
  file that no longer exists (moved/deleted since the project was saved) —
  same "path can go stale" caveat `CellposeImportResult.image_path` already
  lives with. Catch the file-open failure in `set_video_paths` and fall back
  to the empty/import state rather than raising.


────────────────────────────────────────────────────────────────────────────────────────────
NON-GOALS
────────────────────────────────────────────────────────────────────────────────────────────

- Embedding the raw video's pixel data into the `.nseq` archive. Only the
  file path(s) + fps are persisted; the widget must tolerate a stale path.
- `.mp4`/`.avi`/any codec-based video export. Output is a multi-frame TIFF
  (see BACKGROUND point 11) — adding `opencv-python`/`imageio` as a new
  dependency for this is out of scope; ask before adding one if this
  constraint turns out to be unacceptable in review.
- Manual/click-to-place cross positions. Crosses are always derived from
  Cellpose segmentation centroids (per the confirmed design decision) — no
  manual labeling UI.
- Detach-to-separate-window support for this panel (unlike `TraceWidget`/
  `StimWidget`, which support it via `SUPPORTS_DETACH`/a shared `*State`
  class). Treat this the same as `HeatmapWidget`/`SpatialFootprintWidget`,
  neither of which is detachable today.
- Any change to how Suite2p/Cellpose TIFF import itself works. This handoff
  only adds a side-channel path/fps record alongside the existing pipeline
  result — the pipeline's own inputs/outputs/temp-file handling are
  untouched.
- Playing back MULTIPLE videos at once, or per-project video history (only
  the single, most-recently-associated video is kept, exactly like
  `CellposeImportResult` is a single optional slot rather than a named
  collection).
- Any new play/pause/scrub UI on this widget. It reacts to the existing
  shared timeline only (BACKGROUND point 7).
