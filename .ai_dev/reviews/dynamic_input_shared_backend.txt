  StdpSynapticTuning, the Δt-sweep advancement for StdpWindow) is still

  three routines - a large, separate lift), and everything else - gap

ROUND 3 — complete the decision-graph move (MUST-FIX)
--------------------------------------------------------
Decision: push forward rather than accept the Round 2 state. The
`backend_property` pattern already proved the state half of this works
cleanly - this section specifies the same kind of concrete, worked design
for the remaining logic half, using RheobaseDialog as the full worked
example (do this one first, completely, before the other two) and a
mapping table for StdpSynapticTuningDialog/StdpWindowDialog.

The blocker so far has been that decision methods read widget values
directly (`self.spn_min_amplitude.value()`, etc.) and call Qt-touching
methods (`_append_log`, `_update_plot`, block-append-with-camera-follow).
Fix both with patterns already partially established in this codebase:

  (a) Per-run widget values that don't change during a run (amplitude/
      duration ranges, tolerances, neuron ID, thresholds, strategy, etc.)
      get read ONCE into a frozen dataclass by the dialog's `start()`, and
      passed into the backend's `begin_search(config)`. The backend never
      touches a spin box again after that.
  (b) Qt-touching side effects (log messages, plot/heatmap refresh, the
      actual `apply_pattern`+follow-camera write) go through small
      callback hooks on the backend, extending the `on_log`/`on_finished`/
      `on_advance` pattern already in `dynamic_input_routine.py`, and
      through two new methods added to the `SimulationHost` protocol so
      the backend can ask the dialog to append a block without knowing
      about `StimEditor`/Qt at all.
