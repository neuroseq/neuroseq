MUST-FIX
--------

1.  src/neuroseq/example_projects.py:1519-1522 — `_FUER_ELISE_OPSIN_*`
    constants make `stim_exc` visually uninformative.

    Current:

        _FUER_ELISE_OPSIN_EXC_REST: float = 1.0
        _FUER_ELISE_OPSIN_INH_REST: float = 14.0
        _FUER_ELISE_OPSIN_EXC_ACTIVE: float = 1.0
        _FUER_ELISE_OPSIN_INH_ACTIVE: float = 2.0

    Empirically (just verified):

        stim_exc unique values: [1.0]   ← entire heatmap is one colour
        stim_inh unique values: [2.0, 14.0]

    The wrapper's ratio-only semantics means the magnitudes are
    arbitrary, so the ratios that produce u_tgt = -50 mV (active) and
    u_tgt = -70 mV (rest) can be expressed with magnitudes that vary
    in BOTH arrays. The handoff specified the suboptimal pair — that's
    on me, not on Codex — but the empirical result violates the
    user's stim-as-visual-truth principle that motivated this whole
    migration. Worse, the legacy-archive migration in
    `Project._migrate_legacy_elise_stim` produces normalised values in
    [0, 1] that DO vary visibly, so freshly built projects and
    migrated old ones look inconsistent.

    Replace with normalised values that preserve the ratios and stay
    in the [0, 1] range that the migration also uses:

        # Normalised so g_exc + g_inh = 1 in each state; ratios match
        # paper §5.3.3:
        #   active (u_tgt = -50 mV): exc/inh = 1/2  → 0.333 : 0.667
        #   rest   (u_tgt = -70 mV): exc/inh = 1/14 → 0.067 : 0.933
        _FUER_ELISE_OPSIN_EXC_ACTIVE: float = 1.0 / 3.0
        _FUER_ELISE_OPSIN_INH_ACTIVE: float = 2.0 / 3.0
        _FUER_ELISE_OPSIN_EXC_REST:   float = 1.0 / 15.0
        _FUER_ELISE_OPSIN_INH_REST:   float = 14.0 / 15.0

    After this:

        stim_exc varies between ~0.067 (rest) and ~0.333 (active) — 5×
            contrast, easy to spot the pattern in the heatmap.
        stim_inh varies between ~0.667 (active) and ~0.933 (rest) —
            ~1.4× contrast; visible but subtler. Both arrays now show
            the pattern; neither is a flat block.

    Either order is fine (whichever the project's style prefers); the
    important thing is `_EXC_ACTIVE != _EXC_REST` and
    `_INH_ACTIVE != _INH_REST`.

2.  tests/test_example_project_elise.py:149-154 —
    `test_fuer_elise_opsin_stims_default_are_detected_as_periodic` codifies
    the uniform-stim_exc bug.

    Current:

        def test_fuer_elise_opsin_stims_default_are_detected_as_periodic():
            """The default opsin stims remain loop-detectable."""
            from neuroseq.stimulation.stim_loop_dialog import _detect_period

            stim_exc, stim_inh = _build_fuer_elise_opsin_stims()
            assert _detect_period(stim_exc) == 1
            assert _detect_period(stim_inh) == 240

    `_detect_period(stim_exc) == 1` is the smoking gun: period 1 means
    every row is identical = uniform stim. After applying MUST-FIX 1,
    `stim_exc` is no longer uniform and `_detect_period(stim_exc) == 240`
    (one cycle of the Für Elise intro, same as `stim_inh`).

    Replace the assertion:

        def test_fuer_elise_opsin_stims_default_are_detected_as_periodic():
            """Both default opsin stims encode the 240-ms cycle."""
            from neuroseq.stimulation.stim_loop_dialog import _detect_period

            stim_exc, stim_inh = _build_fuer_elise_opsin_stims()
            assert _detect_period(stim_exc) == 240
            assert _detect_period(stim_inh) == 240

NOTES
-----

- `_matching_potential_to_opsins` as a top-level helper (rather than
  inline in `_migrate_legacy_elise_stim`) is a clean improvement over
  the handoff. The migration tests import it and use it as the
  expected-value oracle, which is the right design — the test doesn't
  re-derive the formula independently.

- The handoff also asked for the `tests/test_elise_clamp_visible.py`
  file to be deleted and recreated as `tests/test_elise_opsin_release.py`.
  Done verbatim, plus replacement tests cover every semantic the old
  file did (default-params check, phase-params check, mocked
  bidirectional state preservation, elise-gated integration). No
  regression in coverage.

- `.ai_dev/specs/elise_clamp_visible_toggle.md` got the "Superseded
  by" header note as requested. Don't touch.

- The deletion of `clamp_visible` from `DEFAULT_PARAMS` paired with
  the `Elise.update_params` "drop unknown keys" filter means
  legacy archives carrying `clamp_visible=True` or `False` silently
  ignore that param after load. `tests/test_elise_opsin_release.py::test_clamp_visible_in_legacy_archive_is_dropped`
  confirms it.

- After applying MUST-FIX 1, the spec promotion (next step) should
  document the chosen normalisation explicitly in the
  "## Für Elise example constants" section so future readers know why
  the magnitudes are 1/3, 2/3, 1/15, 14/15 instead of arbitrary
  integers — i.e., "chosen so both arrays show clear active/rest
  contrast in the heatmap, while preserving the ratios that produce
  u_tgt = -50 / -70 mV."
